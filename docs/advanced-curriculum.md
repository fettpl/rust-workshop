## How to Read This Map

The course is to run from the first start of the program for independent design,
maintenance and review of Rust systems. Each stage should have three layers:

1. **Model and practice** — brief example, prediction, launch, observation, explanation and change of code.
2. **Independent proof** — new data, hidden tests, compiler output or public contract API. Passing an
   identical starter is not enough.
3. **Transfer** — two fresh variants, made without a full solution and after at least 24 hours a
   short retrieval task. One variant may be small, the other has to change the domain or
   restriction.

Table status:

- **Works** — path and proof are present in the code, although they still require teaching
  pilotship.
- **In progress** — the work is started, but the stage should not be presented as verified.
- **Plan** — the requirement remains a Curriculum gap.

Complement means path crossing. Mastery requires history of independent evidence:
correct prediction, repair of new error, transfer, delayed retrieval and use in the
project. Self-esteem, reveal and reread are auxiliary signals.

## Spiral portfolio

Each project has a target contract: purpose, required behaviour, evidence, limitations,
adversarial input and retrospective. Projects are to return to older concepts rather
than isolate each stage. The following requirements describe the full portfolio; the
passages implemented are indicated in the first three projects and the full scope of
projects 1–5 remains a plan.

### 1. Number Guessing+

Number Guessing+ retains an old mini-project message, logger variant without `clone` and
saved notes. Four further lessons and the package `number-guessing-workshop` add parser, round state, limited
I/O and a secret drawn once by rand 0.10.2. A single round supports help, wrong entry, EOF,
quit, lose and win the last attempt. The next round is restarted from the terminal;
automatic re-runs and code reading recording from the wider contract below remain an
extension. The technical results are recorded in the verification report.

- **Objective:** safely handle guessing numbers, user input, help, repeating rounds and endings.
- **Behavior required:** input parsing by `Result`, messages for małej/za high value, EOF, empty and incorrect input,
  and trial limit.
- **Evidence:** parser and domain decision tests, border entry test, `cargo fmt`, Clippy and recording a
  short code reading.
- **Limitations:** no `unwrap()` on user data, no global state and no hiding errors by `clone()`.
- **Adversarial inject:** input includes spaces, incorrect number, EOF and value out of range.
- **Artefact:** small Cargo package with README and error decision table.

### 2. Todo CLI

This range assumes one recording and does not promise full durability after power

### 3. Log Analyzer

There is currently a basic version in three lessons and a downloaded Cargo package with
12 files. Parser recognizes `TIMESTAMP LEVEL MESSAGE` and borrows the message; the analysis uses `BufRead` and does
not store the entire entry. The package further limits the stored section of the line to
4096 bytes before LF and skips its excess; simpler exercises `read_line` do not guarantee a
limit of a single line. The reference has 19 tests: 11 unit, 5 integration, 2 process

- **Objective:** stream to analyze a large log without loading the entire file into memory.

- **Evidence:** The current range has tests unit/integration/process/doc, `cargo test`, `cargo fmt`, `cargo clippy`, dev-only benchmark Criterion and

  profile CPU/heap or proof of allocation.
- **Limitations:** wrong lines policy, lack of unlimited `collect`, line fragment limit and constant count

  three model need to be extended.

- **Artefact:** The current library crate with binary, test, benchmark Criterion, result contract,

## Master Command Principles

The minimum proof of valid competence should consist of the following elements:

1. **Prediction without running.** New data and at least one tempting wrong answer.
2. **Encoding or repair.** The task requires the use of a rule, and the Evaluator checks behavior, not just
   process status.
3. **Two transfer variants.** One changes data, the other changes domain, restriction or boundary API. They
   both use fresh tests.
4. **Delayed retrieval.** After a minimum of 24 hours, the person plays the rule and solves a small new
   case without re-reading the solution.
5. **Portfolio use.** The competence appears in the project together with the test, decision and
   retrospective.

The Evaluator must not consider a deliberately mistaken starter to be a success. The
example's copyright verifier now checks starters with the tests and limitations of the
source used by the same evaluator; solutions containing only generic functions are also
compiled and tested. The lack of tests, timeout or infrastructure error does not prove
that the starter needs a proper correction. The missing error API must come from a
diagnostic indicating the original source. The code review checks the contract and
independence of variants alongside automatic control.

The test tasks should include various inputs, empty cases, negative values, `Some(0)`, UTF-8, a
second record and repeated call where relevant. The required idioms or prohibited bypass
should also be checked for modifications when the behavior itself allows you to pass
through literal hardcode. The new generic gateways also use types without `Copy`, `Clone` and
`Debug`, and trait tasks — implementations absent in the starter. Tests in an open local
course are teaching protection, not certified exam.

## Requirements for human evaluation

Technical tests can confirm that the application works, the code compiles and the
evaluator distinguishes success from failure. They do not confirm that the beginner
built the correct mental model or that he transfers knowledge after a break.

Before the stage is identified as a proven teaching pilotage is needed with at least one
person who knows the basics of programming and does not know Rust. The Observer shall
record:

- time to first action and moments of being stuck;
- Prediction before launch, not only the final output;
- an incorrect mental model revealed by a response or code;
- the number and type of hints, reveal and bypass attempts;
- self-repairing a new error;
- the solution to both fresh options;
- a response after a minimum of 24 hours without re-reading;
- user comment on what was difficult and what step helped.

The human column should assess: problem diagnosis, model selection własności/typów, contract
correctness, test quality, decision readability and ability to indicate limitations.
Green build without this evidence is not a seniority assessment. Pilot results should
change the replay queue and content, but not lower points for the error itself.
