### Three approaches

1. Pure typed `authorize(principal, request, grants)` only. Small and directly adjacent to old trust/proof work, but the result can be accidentally reused with another request; it supplies too little Rust-specific integration. Do not choose this alone.
2. **Recommended: scoped grants, monotone attenuation, borrowed-authority/owned-request witness and consuming admission**, plus a dependency-free native package. Four lessons allow each invariant to be explained and assessed independently. Module privacy/ownership are real compiler boundaries, while the policy remains explicitly synthetic.
3. Real authenticated TCP service with credential validation/revocation. More realistic operationally, but requires credential provenance, transport, lifecycle and dependency decisions not established by this local task. It would change multiple independent boundaries and is not A11.

### Data and trust boundary

Use distinct newtypes for principal, tenant and resource identifiers (backed by `u64`, not interchangeable integers in public signatures). `Principal` contains subject and tenant. `Resource` contains tenant and resource id. `Action` is a closed enum `Read | Append`; action sets use the private two-boolean ActionSet with explicit constructor/accessors frozen below, never strings or arbitrary bitmasks. Unknown wire input is deliberately absent: do not invent an authentication parser.

`Request` owns resource, action, declared `cost: u64` and an owned `String` payload. This declared cost is a teaching parameter; it is not measured work or bytes. Do not imply that bounding cost bounds payload memory or CPU. Payload remains present to witness exact request preservation; fixture inputs are bounded authored values.

`GrantSpec` declares one subject, one tenant, `Scope::Tenant | Scope::Resource(ResourceId)`, an action set and a maximum declared cost. The scope always belongs to exactly that tenant. No global wildcard, role inheritance, default administrator, negative grants, or merging privileges across grants. A trusted fixture owner constructs `Authority` from grant specs. GrantSpec being constructible by a safe caller does not make it authoritative; only grants loaded by the service's owner matter. Synthetic principals are supplied by that owner for exercise purposes. Do not accept principal/grant replacement as a special field in an incoming request.

### Operation 1: decide exact-scope authorization

`decide(&self, principal: Principal, request: &Request) -> Result<(), Denial>` is pure. Rule order: different principal/resource tenants yields `TenantMismatch`; otherwise permit only if a SINGLE configured grant matches subject, tenant, scope, requested action, and `request.cost <= grant.max_cost`; otherwise `NoMatchingGrant`. Empty grants, another subject, same resource id in another tenant, missing action and over-cost deny. Ruling uses existential matching of a complete grant; do not combine subject from one grant with action/cost from another. Grant order and duplicate identical grants cannot change the result. Cost 0 and equality are allowed explicitly.

Policy tests need complete positive/negative tables, including a cross-grant 'Frankenstein permission' case and duplicate/permuted grant cases. These test policy decision, not authentication.

### Operation 2: attenuate authority without amplification

`attenuate(parent: &GrantSpec, requested: GrantSpec) -> Result<GrantSpec, AttenuationError>` returns the requested grant unchanged only if subject and tenant are identical, requested actions are a subset, cost maximum is no greater, and scope is contained. Tenant scope can narrow to one resource in that tenant; resource scope can stay at the same resource, never broaden to tenant or switch resource. Empty action set and zero maximum are valid restrictive policies; teach their consequences (zero-cost requests may still be authorized for a nonempty action set). Reject widening rather than silently clipping it, with a single `WouldAmplify` error so error-order trivia does not become an assessment.

This is policy attenuation, not delegating to another identity and not minting a transferable credential. A mathematical bounded oracle enumerates distinct small subjects, tenants, resources, actions and cost boundaries: every request allowed by a successful child must also be allowed by parent. Also assert exact returned child equality; always returning the parent would otherwise satisfy a weak test in some cases. Keep direct literal expected cases independent from the implementation.

### Operation 3: bind the exact owned request to a live authority borrow

`Authority::authorize<'a>(&'a self, principal: Principal, request: Request) -> Result<Authorized<'a>, Denial>` first decides, then moves the exact request into an opaque `Authorized<'a>` with private fields and a retained `&'a Authority` plus principal. No `Clone`, `Copy`, `Default`, public constructor, public fields, `DerefMut`, mutable request accessor, or public unchecked conversion on Authorized; exact derives and accessors for other types are frozen below. Read-only `request(&self) -> &Request` and `principal(&self) -> Principal` accessors expose the original bound values. A public `Authority::replace_grants(&mut self, Vec<GrantSpec>)` demonstrates an explicit local policy update; the retained shared borrow prevents such an update while a witness will still be used.

Retain the actual authority reference, not merely `PhantomData` or a copied authority id: this is the chosen pedagogical API contract, not a claim that PhantomData can never represent lifetime relationships. For clarity use a private consume/destructure helper accessed only within the authority/service implementation, so safe downstream code cannot extract and swap internals. The field need not be dereferenced during admission to bind its lifetime; do not teach that an underscore-named lifetime field permits dropping the relationship.

External safe consumers can construct requests and a separate test authority; they cannot fabricate an Authorized for an existing authority, mutate its bound request, extract a replaceable request, clone the witness or reuse it after move. They may intentionally obtain a second authorization from the same unchanged authority: no single-use global credential or duplicate-operation guarantee is claimed. Authorized values may be dropped without admission and without accounting. Rust ownership is affine, not a promise that a value must be used.

**Revocation scope:** retained immutable borrowing prevents *local* `replace_grants` while a witness remains live and subsequently used. It is not a distributed revocation mechanism or guarantee against wall-clock expiry. After the old witness is consumed/dropped, updating policy affects subsequent authorizations. No interior mutable policy; no serialized or persisted witness; no expiry claim. Do not claim tokens survive policy change safely or automatically reauthorize.

### Operation 4: consume authorization before admission accounting

Use an internal `admit(Authorized<'_>, &mut AdmissionState) -> Result<Accepted, AdmissionRejection>` and public facade `Service::submit(&mut self, principal, request) -> Result<Accepted, SubmitError>`. Service owns a private Authority and private AdmissionState; its constructor is a trusted-host setup API. `submit` always authorizes using its own authority, then calls internal admission. There is **no public submit-authorized-witness API** through which a ticket from authority A could be submitted to service B. Direct policy-level authorization exists for teaching/privacy probes; service execution remains bound to its configured authority. Use ordinary Rust disjoint field borrowing to obtain `&self.authority` and `&mut self.state`; do not clone or loosen the witness to satisfy the borrow checker.

AdmissionState contains accepting flag, accepted count, accepted limit, charged cost and cost limit, all counters/limits `u64`. It is a finite accepted-work ledger, not an active-connection semaphore or completion/drain simulation. No decrement or completion operation in A11. Check, in order: accepting; checked accepted+1 and capacity; checked charged+request.cost and aggregate cost limit. Distinguish `Closed`, `Capacity`, `CostBudget`, `CounterOverflow` (overflow before corresponding capacity test). Compute both next counters before any write. On any failure, leave both counters exactly unchanged and perform no accepted-record append. On success update both and return an Accepted record carrying exact principal and original owned request. Native tests inspect that record; no storage/TCP side effect is claimed.

Public submission returns `SubmitError::Denied(Denial)` before admission errors. Even when closed/full, a denied request is denied and state remains unchanged. Authorized + full returns a capacity error, not denied. Declared cost equality with remaining budget succeeds; one above denies admission. Values near MAX prove checked arithmetic and atomic failure in debug and release profiles. Consuming an authorization once does not prohibit a new request being authorized again, and accepted does not mean completed, persisted or delivered.

### Native package canonical algorithm handoff and equivalents

Canonical decide starts `if principal.tenant != request.resource.tenant { return Err(Denial::TenantMismatch); }`; then `self.grants.iter().any(|grant| { ... })` combines subject equality, tenant equality, exact/tenant scope, action contains and `request.cost <= grant.max_cost` within one closure. Equivalent uses an early-return loop with those same conditions; it must not call canonical decide. Canonical attenuation explicitly rejects subject/tenant mismatch, failed subset, larger maximum and non-contained scope, then `Ok(requested)`; equivalent computes each containment boolean in match expressions then combines them. Canonical authorize calls self.decide with borrowed request using `?`, then returns `Ok(Authorized { authority: self, principal, request })`; equivalent uses explicit match and identical exact move, not cloning/reconstructing selected fields. Canonical admit destructures witness, checks closed, computes `next_accepted = state.accepted.checked_add(1).ok_or(CounterOverflow)?`, capacity, then `next_cost = state.charged_cost.checked_add(request.cost).ok_or(CounterOverflow)?`, budget, then commits both fields and returns Accepted. Equivalent computes checked candidates in match expressions and commits a new AdmissionState only after all checks, preserving error order. All four equivalent source variants are independent implementations, not aliases calling canonical code.
