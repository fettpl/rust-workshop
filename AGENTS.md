# Repository guidance

## Product and language

Rust Workshop is a local-first learning workspace for people with basic
programming knowledge and no Rust experience. Explain Rust from first
principles; do not assume knowledge of another language's libraries.

Learner-facing lessons, prompts, feedback, and interface copy are Polish.
Contributor documentation, commits, pull requests, and agent notes are
English. Describe only capabilities that exist. Do not invent accounts, cloud
sync, hosting, educational efficacy, professional readiness, or an automatic
whole-architecture assessment.

## Repository map

- `src/content/` contains lessons, modules, concepts, reviews, sources,
  evaluator contracts, and project definitions; `src/content/course.ts`
  assembles the catalog.
- `src/engine/` owns evaluation, learning evidence, review, and navigation.
  Keep those rules separate from UI components.
- `src/persistence/` owns IndexedDB state, validation, migration, and
  import/export. `src/runner/` and `src/app/api/run/` own the remote Rust
  execution adapter and route.
- `src/domain/` holds shared types and trusted-fixture contracts. `scripts/`
  contains maintainer verifiers and the project-asset generator. `tests/`
  contains browser and integration checks. `public/projects/` contains
  generated archives and must be regenerated by the package script.
- `docs/` contains durable specialist guidance, verification boundaries, and
  maintained evidence. The current CI contract is [docs/ci-cd.md](docs/ci-cd.md);
  the runner boundary is [docs/runner.md](docs/runner.md).

## Commands and test selection

Use a supported Node.js version from `package.json` (`^22.23.4 || ^24.22.1 || ^26.12.1`) and
install the locked dependency graph with:

```sh
npm ci
```

`npm run dev` and `npm run build` run the lifecycle asset generator. Use
`npm run dev` for local development and `npm run build && npm start -- --port 3002`
for a production server. Never hand-edit generated project archives.

Choose checks from the changed surface:

- TypeScript, React, scripts, or shared types: `npm run lint`,
  `npm run typecheck`, and focused Vitest or Node tests.
- Lessons, evaluators, sources, or project packages: `npm run content:check`,
  `npm run content:rust`, the affected `content:*` verifier, and the relevant
  trusted Rust package check. Run `npm run content:packages` before inspecting
  generated archives; commands with `--fetch` prepare their locked fixture
  dependencies, while subsequent checks are offline and locked.
- Persistence, runner, or browser behavior: focused unit tests plus the
  relevant Playwright suite. Production E2E and `npm run test:offline` require
  a production server and Playwright Chromium; see [docs/ci-cd.md](docs/ci-cd.md).
- A broad change: run `npm run lint`, `npm run typecheck`,
  `npm run content:check`, and `npm test`, after preparing the stable Rust
  toolchain and the fixed Tokio cache described in [docs/ci-cd.md](docs/ci-cd.md).

`npm test` includes trusted native-fixture tests. The initialized-prefix unit
proof may skip in an ordinary local run when its authorization inputs are
absent. An authorized run requires CI's offline Cargo configuration, stable
`rustc`/`rustdoc`/`cargo` qualification, executable paths and awaited proof
artifacts; do not bypass qualification or turn a missing executable, timeout,
dependency failure, or incomplete report into a pass or a convenient skip.
Report blocked, infrastructure-limited, partial, and skipped runs accurately.

Specialized checks have explicit prerequisites: exact Rust `1.85.0` for MSRV
coverage; nightly `2026-08-08` with Miri and `rust-src` for Miri coverage;
`cargo-fuzz 0.13.2` for the mini-grep campaign; and Valgrind for fresh
Callgrind evidence. Their verifiers record tool paths, versions, and evidence
metadata. A dependency fetch is preparation, not behavioral proof. Miri and
other undefined-behavior metadata describe the repository-authored native
fixture only; they are never evidence that arbitrary learner code is safe.

## Authoring and evidence contracts

Follow the types and existing patterns in `src/content/` and
`src/domain/types.ts`. Keep official source links and reviewed metadata
current; a link is not executable proof. Validate examples and evaluator
contracts against the supported compiler/tool versions, and retain the
actual compiler, tool path, version, and SHA or other provenance in reports
where the verifier requires it.

Lesson, module, concept, review, task-family, source, and project IDs are
persistent contracts. Preserve historical step order and identities. When a
change needs a new identity or migration, make that compatibility handling
explicit. Preserve exact resume position, drafts, notes, bookmarks, raw
evidence history, assistance history, review sessions, and imported state.
Never rewrite old events to manufacture evidence or silently discard imported
records.

Keep exposure, completion, independent coding, and delayed retrieval as
separate evidence. A reveal, hint, assisted submission, alias, repeated task,
or mocked runner response cannot become independent coding credit. Importing a
record cannot create, upgrade, or relabel independent credit by itself; preserve
already-valid historical independent events and their provenance, timestamps,
IDs, and evidence class unchanged. Primary tasks, completion state, and
review/retrieval tasks each have their own contracts; preserve those
distinctions when changing evaluators or navigation.

Learner Rust entered into or imported by the app runs only through the
`POST /api/run` endpoint and the isolated remote runner adapter. The app and
maintainer verifiers must never execute learner or imported files, arbitrary manifests, or
browser-provided tool choices with local `rustc`, Cargo, a shell, or child
processes. A learner may run a downloaded Cargo archive in the learner's own
environment; that personal workflow is separate from app and agent automation.
Runner unavailability is infrastructure feedback, not a wrong answer; offline
study preserves state and explains that execution is unavailable. Intercepted
browser responses prove request/UI/state behavior only.

Local Rust verifiers are maintainer tools for fixed, repository-authored,
trusted fixtures. Keep their inputs closed over authored files and fixed
manifests. They must reject arbitrary source, paths, dependency overrides, and
arbitrary toolchain selectors; documented fixed toolchains such as exact Rust
`1.85.0` for `--msrv` remain supported where a verifier documents them. Native
execution, mutation controls, Miri, profiling, fuzzing, and compiler
diagnostics are evidence for their declared fixture scope only, never a hidden
local runner for learners or a whole-product safety claim. Stable and MSRV
checks may execute authored `safe-behavior` fixture checks. Authored
undefined-behavior negative fixtures use metadata-only compilation and are
selected only by pinned Miri; they are never executed natively, including with
fixed trusted inputs. Miri and undefined-behavior metadata authorize no native
execution of learner or imported code. Use
[docs/initialized-prefix-evidence.md](docs/initialized-prefix-evidence.md) for
the maintained initialized-prefix boundary.

## Collaboration and review

Make small English commits with one coherent feature per pull request. Keep
parallel work on disjoint files and state the ownership boundary before
editing. Persist resume and handoff notes in an ignored repository-relative
directory such as `test-results/handoff/`; do not rely on temporary folders and
do not commit private receipts, credentials, account details, or machine paths.

Obtain independent review for substantive changes. Treat automated review
comments as hypotheses: reproduce the alleged behavior, inspect the relevant
contract and tests, and resolve or document the finding only after technical
verification. Do not treat an agent review as legal advice.

Before integration, require fresh checks on the exact PR head, independent
review, and the repository's ordinary merge path. After the merge, verify the
resulting `main` commit. Historical green runs, a different commit, a mocked
runner, a dependency fetch, or a partial local run do not satisfy a current
required check. If required CI or infrastructure is unavailable, keep the
work local and report the limitation; never bypass a gate or manufacture a
success.

All maintainer-dispatched subagents use GPT-5.6-Luna with high reasoning. Do
not silently substitute another model; report unavailability. An explicit
later user instruction takes precedence. This is a maintainer workflow
preference and is not a paid-tool requirement for outside contributors.

## Human decisions and safety boundaries

Implementation instructions authorize in-scope reversible repository work.
They do not authorize choosing or finalizing licenses or copyright credit,
publishing or changing repository visibility, deployment or hosting, package
publication, billing or paid infrastructure, or destructive operations.
Those actions require the maintainer's explicit decision and any applicable
fresh review and checks. Preserve evidence and history; do not rewrite history,
delete records, or remove security controls to make a report green. Keep
project-specific temporary holds and account state in private root instructions
or ignored handoff state, not in this evergreen guide.

For workflow security, keep least-privilege permissions, untrusted fork code
away from secrets and privileged triggers, and do not use maintainer machines
for untrusted PR code. This repository currently pins third-party actions by
full commit SHA as a project choice; GitHub's current guidance describes
workflow dependency lockfiles as the strongest option where the repository can
adopt them, with full-SHA pins as the fallback. Recheck the official guidance
when changing the workflow.
